# Strange Battle — инструкции разработки

## Применение правил

Перед изменениями прочитай `.agents/global-agent-rules/AGENTS.md`.
Это локальная копия предоставленных пользователем общих правил. Исходные
документы сохранены в `.agents/global-agent-rules/` без изменений.

Соблюдай инструкции среды и явные указания пользователя; этот файл уточняет
общие правила для проекта. Вложения задают подход к работе, но сами по себе
не являются запросом реализовать перечисленные в них системы или инструменты.

Проект не использует Unity или C#. Соответствующие разделы общих правил и
`code-style.md` сейчас неприменимы. Упомянутые в исходном README каталоги
`pipelines/`, `templates/`, `skills/`, `scripts/` в предоставленный комплект
не входили. Не пытайся запускать отсутствующие инструменты, устанавливать
Unity skill или использовать пути `F:\VIBECODE` из примеров.

## Текущий проект

- Strange Battle, версия в `package.json`: 1.9.0.
- JavaScript, Canvas 2D, Electron; зависимости и их версии — в
  `package.json` и `package-lock.json`.
- `main.js` — процесс Electron, CommonJS. Сохраняй `contextIsolation: true`
  и `nodeIntegration: false`.
- `index.html` загружает `game.js` как ES module; `game.js` создаёт игру через
  `src/engine/create-game.js`. `src/package.json` задаёт ES modules для `src/`.
- `src/engine/` — сборка игры, состояние, ввод, конфигурация, эффекты и звук;
  `src/entities/` — бойцы; `src/characters/` — персонажи;
  `src/systems/` — игровые системы; `src/ai/` — ИИ;
  `src/rendering/` — отрисовка; `src/ui/` — интерфейс.
- Существующая сборка связывает модули через контекст игры и `register`.
  Перед изменениями проследи регистрацию и итоговое назначение функций в
  `create-game.js`: реализация может переопределяться другим модулем.
- HTML-файлы `SB JAPAN UPD.html` и `SB 1.7 china — копия.html` не являются
  точками входа текущего приложения. Сохраняй их как исходные материалы;
  не синхронизируй с ними изменения автоматически.
- GitHub проекта: `https://github.com/Saikerrr/strange-battle` (публичный).
  Основная ветка — `main`. Перед глобальным патчем сохраняется тег
  `checkpoint/pre-global-patch`.
- По запросу пользователя сохраняй чекпоинты: перед крупными изменениями
  и после проверенных этапов делай осмысленный commit и push в рабочую ветку.
  Большой патч веди в отдельной ветке; не сливай её в `main` без согласования.
  Это чекпоинты по этапам работы агента, не фоновое сохранение по таймеру.
  При ошибке push сохраняй локальный коммит и сообщай, что копия на GitHub
  не обновлена. Не используй force push и не включай секреты в коммиты.

## Порядок работы

1. Изучи затрагиваемый код, существующие проверки и актуальные документы.
   Сохраняй изменения пользователя. Не запускай скрипты миграции и
   реорганизации из `scripts/` без понимания их эффекта и необходимости.
2. Для существенной функции зафиксируй цель, поведение, границы, интеграции,
   критерии приёмки и допущения по Feature Readiness из общих правил.
   Выясняй факты по коду; уточняй у пользователя только существенные
   неразрешённые вопросы. Явно делегированные решения принимай самостоятельно.
3. Реализуй минимальное целостное изменение в существующей структуре.
   Следуй стилю соседнего JavaScript и настройкам Prettier. Не добавляй
   фреймворки, новые слои или зависимости без текущей необходимости.
4. Не меняй самовольно баланс, управление, состав персонажей, тексты,
   прогрессию и художественное направление. Обычные обратимые технические
   решения в согласованной задаче выполняй автономно.
5. Проверь изменённое поведение и обнови относящиеся к нему документы.
   Сообщай результат, проверки и существенные ограничения по-русски,
   кратко и без обязательных заголовков для мелких задач.

## Запуск и проверка

Все команды выполняются из корня проекта:

- `npm start` — запуск игры в Electron.
- `npm run dev` — запуск с DevTools.
- `npm test` — Node tests с подменённым Canvas/DOM: персонажи, способности,
  ИИ, интерфейс, сброс состояния, пауза и ввод.
- `npm run test:electron` — проверка в настоящем Electron: 36 сочетаний
  персонажей, отрисовка, ультимейты, конечность координат и ошибки консоли.
  Она не заменяет ручную проверку управления, звука и игрового ощущения.
- `npm run format:check` — проверка форматирования исходников и тестов.

Выбирай проверки по изменению. Для правок только документации проверь пути,
ссылки и соответствие фактам; запуск игры не обязателен. Для игровой логики
запускай релевантные автопроверки; для ввода, UI и отрисовки проверяй также
поведение в Electron. Не выдавай тест с заглушками за ручной плейтест.
Невыполненные необходимые проверки помечай `degraded` с конкретной причиной.

Артефакты сохраняй в проекте. `scripts/test-electron.cjs` пишет проверочные
снимки в `artifacts/verification/`; их назначение описано в README этого
каталога. Резервная копия исходных модулей хранится в `backups/`.

## Поддержка инструкций

Пользователь разрешил уточнять инструкции по ходу разработки. Обновляй этот
файл при подтверждённых изменениях команд, структуры, договорённостей или
при обнаружении повторяющейся ошибки. Кратко сообщай о существенных поправках.
Не превращай единичный случай в универсальный запрет и не расширяй игровую
задачу под видом обновления правил.

Проектные уточнения веди здесь; общие документы меняй только для обоснованных
повторно используемых правил. Если появится многоэтапный план, используй
`gamedesign/DEVELOPMENT_PLAN.md`, если к тому времени не будет другой
канонической точки. Не создавай план, журнал или архитектурный документ
только ради формальности. Перед работой проверяй появившиеся документы и
вкладывай результаты в существующий источник истины.
